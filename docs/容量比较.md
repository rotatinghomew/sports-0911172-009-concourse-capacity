# 容量情景比较方法

`analysis.coverage` 与 `analysis.evaluate` 回答“中场十五分钟，加开窗口与提前备餐哪个更有用”这类问题。比较从现有队列、收款、备餐与排班记录出发，把候选方案放在同一批历史场次上整场回放，不按成交平均耗时倒推窗口数。

## 观察边界

历史票据并不完整，比较时保留边界、不补写未观测事实：

- **仍在队中**（`waiting`）：等待时长只知下界，按删失处理，不计为零等待，也不当作已服务。
- **未知时刻**（`at` 为 null 的事后补记）：`recorded_at` 是登记时刻，不替代实际取号。此类票据计入需求与未服务比例，但不进入等待分布与耐心分布；回放中按登记时刻到达只是明确声明的分析假设。
- **真正无等待**：叫号时刻等于取号时刻的成交，才是等待为零。
- **中途离队**（`abandoned`）：没有完整服务时间，其等待按删失保留到离队时刻；耐心分布由离队（事件）与被叫号/仍在队中（删失）用 Kaplan-Meier 估计。

等待分布、耐心分布均以生存曲线表达，中位数读自曲线，不是成交样本的算术平均。

## 整场回放

- 评估单位是**整个场次**：同一场各窗口共享同一股人流与同行观众，不逐窗截取各自最好的一段拼接方案。
- 同行观众（`party`）共享同一耐心阈值，同时离队。
- 每个方案 × 每场 × 多次重复回放使用同一批预抽的服务时间、耐心与收款样本（配对种子），方案间差异才可比。
- 基线窗口数按该场实际发生叫号的窗口计；方案班次按当日时刻映射到历史场次，只比较时段结构。
- 服务可延续到取号后 `service_horizon_minutes` 分钟；`window_minutes` 内的完成比例单独报告。
- 备餐是真实容量维度：每场可用份数来自历史备餐记录加方案备餐，售罄即停售；剩余份数按 `serving_cost_cents` 计入净收益。

## 历史检验与不能推荐的范围

`evaluate` 先用基线方案回放历史场次，对照实际观察的等待分布、未服务比例与毛收款（`validation`）。以下情形**不推荐任何方案**，只给出指标供参考：

- 完整服务时间样本少于 `min_service_sample`；
- 未知取号比例可控（≤ `unknown_share_limit`）的场次少于 `min_matches`；
- 没有已收款记录；
- 基线回放的未服务比例平均误差超过 `validation_unserved_limit`（容量模型未通过历史检验）。

`coverage` 中的 `max_concurrent_service` 可用于判断窗口数是否代表产能上限：同时处于服务中的票据数远超窗口数时，记录不支持“窗口数即产能”的读法，该场会被标记。

## 约束与表现同次比较

`constraints.immovable` 指定不可移动的员工；`constraints.window_skill` 指定窗口所需技能。每个方案先按当前记录核对：员工存在且未请假、技能匹配、不与现有班次冲突、同一方案内一人不同时上两个窗口、食材现有量覆盖方案备餐。未通过核对的方案只列出违例，不产生指标，也不进入推荐。

## 未验证假设

报告 `assumptions` 逐条列出，包括：补记票据按登记时刻计入需求、共享队列、跨场次分布稳定、同行同时离队、备餐加速秒数与剩余成本取值、服务延续时长、基线窗口口径、班次时刻映射。其中备餐加速与剩余成本是**未验证假设**，记录中没有对照证据；结论对这些取值敏感时应改值重跑，而不是沿用单次结果。

## 比较、采纳与追溯

- `analysis.evaluate` 只读业务记录并写入评估档案（`evaluation`），不占用真实班次或食材。
- `scenarios.save` 可带 `evaluation` 引用，把采纳理由与评估档案挂到情景上；`save` 仍不占用资源。
- `scenarios.adopt` 在单事务中按**当时**记录重新核验并执行。分析之后有人请假或食材报损，核验失败则整个采纳回滚，旧建议不会直接变成班表；核验通过但所引评估的输入已修订时，采纳记录会标注 `input_changes`，此时应重新评估而不是沿用旧结论。
- 已执行的安排可通过 `Store.history('scenario', id)` 找回当时说明与评估编号，评估档案中保存完整输入、配置、快照与报告。

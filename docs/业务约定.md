# 当前业务约定

队列 at 是实际取号时刻，可为 null；recorded_at 是登记时刻，不替代实际取号。未完成队列保留状态。技能与班次为左闭右开区间，备餐消耗真实食材。scenario 仅保存人工安排，save 不占用资源；adopt 在单事务中核验并执行，不提供等待分布预测。analysis 只读记录做容量比较，比较口径与不能推荐的范围见 `docs/容量比较.md`。

## 数据与一致性

金额均为整数分；日期使用零补齐的日期或同一时区时间字符串，跨时区输入应由调用方先规范化。所有 ID 为业务编号。写入会增加修订并保留旧值，历史 `recorded_at` 是登记时间，不等于事实发生时间；不能据此推断未观测到的业务事实。

单次业务操作是一个事务，失败不留下中间结果；整份回放按顺序逐项执行，前一项成功不会因为后一项失败而撤销。现有重复编号拒绝语义及已完成状态的重试语义由业务操作维护。操作台 JSON 中 `results` 是操作结果，`state` 为当前业务记录；历史以 `Store.history` 查询，当前状态与历史不能混为一谈。

## 已有操作

- `queueing.issue(id, party, at, recorded_at, window)`
- `queueing.call(id, at)`
- `queueing.abandon(id, at)`
- `queueing.complete(id, at, cents)`
- `kitchen.stock(id, units)`
- `kitchen.prepare(id, ingredient, units, servings, at)`
- `kitchen.consume(id, count)`
- `kitchen.waste(id, units)`
- `staffing.worker(id, skills)`
- `staffing.absence(id)`
- `staffing.assign(id, worker, window, skill, start, end)`
- `scenarios.save(id, shifts, preparation, reason, evaluation=None)`
- `scenarios.adopt(id)`
- `analysis.coverage(window_minutes, min_service_sample, unknown_share_limit)`
- `analysis.evaluate(id, plans, constraints, assumptions, matches)`

`analysis.evaluate` 把评估输入、配置、人员与食材修订快照和完整报告存为 `evaluation` 业务记录，编号重复同样拒绝。`scenarios.save` 可引用 `evaluation`；`adopt` 时若所引评估的输入自分析后已修订，会在采纳记录中标注 `input_changes`。

直接方法调用和本地操作台使用相同的业务服务。`data/demo.json` 展示一条正常经营路径，并不代表总体人群；它不适合用来宣称任何统计规律。扩展分析时应另外构造能辨别缺失、覆盖和信息时间的样本，不得把样本中的关联直接当成因果结论。
